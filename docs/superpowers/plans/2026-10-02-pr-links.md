# PR descriptions link the spec and plan at a commit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In this repo the flow in `docs/way-of-working.md` §1–2 applies (implementer and task-reviewer agents, the `Model:` tag, waves).

**Goal:** `docs/way-of-working.md` §1 step 6 says that a PR description links the spec and plan at a pushed commit, by its full SHA, and the PR template's comment points to that step (#101).

**Architecture:** one task adds two sentences at the end of §1 step 6, and replaces the one comment line in the PR template. The spec fixes the wording; this plan fixes the line breaks too.

**Tech Stack:** Markdown only. No code and no tests change.

**Spec:** `docs/superpowers/specs/2026-10-02-pr-links-design.md` (issue #101).

## Global Constraints

- **Nothing private (hard rule 3):** no IDs, tokens or emails, no real-instance data, and no local absolute
  path of a worktree: not in the two files, not in the commit message, and not in the report's quoted
  commands where a placeholder does. The link form is written with `<owner>`, `<repo>`, `<full sha>` and
  `<path>`, as placeholders.
- **Docs principles (`way-of-working.md` §7):** each fact lives in one place. The link form is stated in §1
  step 6 only; the template's comment points there and states no form.
- **The wording is fixed:** the text in Task 1's blocks lands exactly as written there, line breaks
  included. "full SHA" stays on one line.
- **Only two places change:** the last line of §1 step 6 in `docs/way-of-working.md` (plus three new lines
  after it), and line 3 of `.github/pull_request_template.md`. Don't reword neighbouring text: the rest of
  step 6 stays as it is, and so do step 10 and §8. Don't touch any other file: not `.claude/`, `scripts/`,
  `.pre-commit-config.yaml`, `.github/workflows/`, `CLAUDE.md`, `docs/decisions.md`, `docs/notes.md` or
  `CHANGELOG.md`.
- **Gates before the commit** (`CLAUDE.md` → Commands): `uv run pytest -q`, then `uv run ruff check && uv
  run ruff format --check && uv run mypy && uv run actionlint && uv run zizmor --offline .github/workflows`.
  The coverage gate (`uv run pytest --cov=custom_components.nortec_go --cov-report=term-missing
  --cov-fail-under=95`) too.
- **Every command runs in the issue worktree:** `cd <worktree> && …`, or `git -C <worktree> …`. The dispatch
  gives the worktree's absolute path. Edit files by absolute path under it.
- **Commit message:** write it with the Write tool to `/tmp/pr-links-task-1-msg.txt` and commit with
  `git commit -F <file>`. No heredocs. End the message with the co-author trailer given in the dispatch. The
  title starts with `process:`.
- **Never push.** The team lead pushes.
- **Stop instead of widening:** if the work turns out to need a decision-log entry, or an edit to a hard
  rule, `.claude/`, `.pre-commit-config.yaml`, `.github/workflows/` or `scripts/`, stop and report it; the
  team lead sends it to the PO as `blocked` (the spec's *Risks*).
- **PR:** title `process: PR descriptions link the spec and plan at a commit (#101)`. It doesn't release, so
  there is no `CHANGELOG.md` entry and no bump.

## Review Focus

Docs have no tests here, so each line names the check that pins it.

1. **A wrap splits "full SHA", or the URL form, and the spec's first search finds nothing.** Pinned by
   Task 1, Step 3's first search and its greps for the four lines.
2. **The old template comment stays beside the new one.** The spec's second search still gives one hit
   then. Pinned by Task 1, Step 3's third search (no hit) and by `git diff --numstat`.
3. **The template states the link form too.** That would put the form in two places (§7). Pinned by
   Task 1, Step 3's grep for `blob` in the template (no hit) and by the task review.
4. **The rest of step 6 is reworded.** Its first two lines, and the sentence "The owner reviews the spec and
   plan there.", stay as they are. Pinned by Task 1, Step 3's greps for those lines and by the one removed
   line per file in the diff.
5. **This work breaks its own rule:** its PR description links the spec and plan on the branch, by a short
   SHA, or at a commit that doesn't hold the file's current text. Not a task's check: the team lead runs it
   (*The check on this work's own PR*), first right after opening the draft PR, so before Task 1, and again
   before `branch ready`.

## The check on this work's own PR

The team lead runs it twice: right after opening the draft PR (so before Task 1), and again before
`branch ready`. It is the spec's check: both links have the new form, each names a pushed commit that holds
that file's current text, each opens the file, and no link names the branch.

The description holds no other `https://github.com/…/blob/…` URL: it names other PRs by number, and its
prose describes the link form in words ("a link to a commit, by its full SHA") without writing the URL
form out, not even with placeholders: the first `grep` below would match that too. Otherwise the "two URLs
and no more" fails.

First save the description, so that a failing `gh` isn't hidden behind a pipe (`docs/notes.md`, "A piped
gate hides its exit code"):

```bash
gh pr view --json body --jq .body > /tmp/pr-links-body.txt
```

Expected: exit status 0, and the file isn't empty.

```bash
grep -oE 'https://github\.com/[^) ]+/blob/[^) ]+' /tmp/pr-links-body.txt
```

Expected: two URLs and no more. Each has 40 hexadecimal characters right after `/blob/`. One ends in
`/docs/superpowers/specs/2026-10-02-pr-links-design.md` and the other in
`/docs/superpowers/plans/2026-10-02-pr-links.md`.

```bash
grep -oE 'blob/[0-9a-f]{40}/docs/superpowers/(specs|plans)/2026-10-02-pr-links' /tmp/pr-links-body.txt | wc -l
grep -c 'blob/docs/pr-links/' /tmp/pr-links-body.txt
```

Expected: `2` (a count of links, not of lines; the description is already saved, so the pipe hides no
failing `gh`), then `0`.

For each of the two links, with `<sha>` and `<path>` taken from it:

```bash
git fetch origin
git merge-base --is-ancestor <sha> origin/docs/pr-links
git diff --quiet <sha> origin/docs/pr-links -- <path>
```

Expected: exit status 0 from each: the commit is pushed, and the file at that commit is the file on the
branch's head.

```bash
curl -s https://github.com/<owner>/<repo>/blob/<sha>/<path> | grep -o '<title>[^<]*</title>'
```

Expected: one title, which names `<path>` and `<sha>`. A title that names the login page, `File not found ·
GitHub`, or no title, is a failure, whatever the status was (the spec's last fact).
